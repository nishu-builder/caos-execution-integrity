Notes on Caos and agent safety

Caos makes an agent's work easier to name, retain, and inspect. A tool, its inputs, and its result can be represented as Git objects, so another person can examine the same bytes. That is useful for safety work, but it leaves important questions about who controls execution, which effects are observed, and what a recorded result actually establishes.

These small experiments make some of those questions concrete. Each uses real Caos jobs and deliberately limited fixtures. The attacks are fixed scripts, so the results tell us about particular boundaries rather than an adaptive model's chance of breaking them.

The examples below show both improvements and their limits. All effects are local fixtures; the private-data example uses an explicitly fake canary.

What this lab establishes

These are mechanism demonstrations, not a deployable safety system. They run on one host with fixed attack scripts, short-lived keys, in-memory ledgers, and serial handlers. We have not tested human approval, authorization recovery after crashes, concurrent attacks, or an adaptive agent. Deployment would still need a protected review and display path, durable authorization, and controls on every route that can cause an external effect.

Rerun the examples

The complete worker images and inputs are available as Git objects on the caos-rerun branch and in a downloadable bundle. From a clone of the repository, with a compatible Caos server running:

python3 reproduce.py run --server http://localhost:9090

This reruns 32 worker jobs with fresh cache keys and compares the complete result trees with the published results. All 32 matched in our validation. The live services and surrounding safety controls still need the full demo runner. See the reproduction guide for setup and individual examples.
